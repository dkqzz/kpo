# ДЗ №3. ВышBuild

Веб-приложение для приёма домашних работ и синхронной проверки их исходников.
Студент загружает файл, преподаватель видит результаты всех сдач по заданию.

## Запуск

Нужны Docker и Docker Compose. Из корня репозитория выполните

```bash
cd task_3
docker compose up
```

- [Веб-интерфейс](http://localhost:8000/) принимает файлы и показывает карточки
  проверок и сводку.
- [Swagger UI](http://localhost:8000/docs) позволяет выполнить ключевые запросы.
  Его скрипты загружаются с CDN.
  [Схема OpenAPI](http://localhost:8000/openapi.json) доступна локально.

У Gateway один опубликованный порт на `127.0.0.1:8000`. Store и Analysis
доступны внутри сети Compose. Файлы и базы сохраняются в двух именованных томах
при обычном `docker compose down` и последующем запуске.

## Архитектура

| Компонент   | Ответственность                                                                    | Данные                                                |
| ----------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `store/`    | Принимает артефакт, фиксирует факт сдачи, выдаёт файл и метаданные                 | Файлы под UUID и `submissions.sqlite3` в `store-data` |
| `analysis/` | Получает артефакт из Store, проверяет его и выдаёт сохранённый отчёт               | `reports.sqlite3` в `analysis-data`                   |
| `gateway/`  | Принимает клиентские запросы, вызывает сервисы, собирает сводку и отдаёт интерфейс | Данные запроса                                        |

У каждого компонента свой процесс Flask и свой Dockerfile. Общий пакет `common/`
содержит обработку HTTP-ошибок, валидацию формы и открытие транзакций SQLite.
Каждый сервис открывает только свою БД. Для запросов между сервисами
используется HTTPX с таймаутами. Роль пользователя задаётся сценарием
использования, а задание идентифицируется переданным `assignment_id`.

### Как проходит сдача

1. Студент отправляет `POST /submissions` в Gateway. Форма `multipart/form-data`
   содержит `student_id`, `assignment_id` и `file`.
2. Gateway отправляет форму в Store на `POST /submissions`. Store выделяет UUID,
   сохраняет файл и регистрирует сдачу с датой, именем и размером файла.
3. Gateway вызывает `POST /reports/{submission_id}` в Analysis. Analysis читает
   метаданные и артефакт из Store через `GET /submissions/{submission_id}` и
   `GET /artifacts/{submission_id}`. Затем он сохраняет отчёт и возвращает его.
4. Gateway возвращает `201 Created` с полями `submission` и `report`. В отчёте
   есть `status`, `success`, описание проверки и время её выполнения. Даже
   красный отчёт возвращается с `201`, поскольку сдача и отчёт были созданы.

Преподаватель открывает `GET /submissions/{submission_id}/report` для одной
сдачи. Для `GET /assignments/{assignment_id}/reports` Gateway объединяет сдачи
из Store и отчёты из Analysis по UUID. Сдачи идут от новых к старым. Сводка
содержит общее количество, прошедшие проверку, проваленные и сдачи без отчёта.

### Что происходит при сбое

| Ситуация                                                             | Результат                                                                                          |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Не удалось связаться со Store при загрузке                           | Gateway возвращает `503` и `error.service: "store"`. Анализ не запускается.                        |
| Store сохранил работу, затем Analysis стал недоступен                | Gateway возвращает `503`, имя сервиса и `error.submission_id`. Файл и метаданные остаются в Store. |
| Сервис превысил таймаут                                              | Gateway возвращает `504`. Если Store подтвердил сохранение, ответ содержит ID сдачи.               |
| Внутренний сервис вернул неожиданный HTTP-статус или невалидный JSON | Gateway возвращает `502` с именем сервиса.                                                         |

После восстановления Analysis сохранённая сдача без отчёта отображается в сводке
со статусом `no_report`. В интерфейсе для неё есть кнопка «Повторить анализ»,
которая вызывает `POST /submissions/{submission_id}/analysis`. Этот запрос
переиспользует существующий отчёт или создаёт его для сохранённого файла.

## Алгоритм проверки

1. Пустой файл получает красный отчёт. Для самостоятельного `.py` проверяется
   его содержимое. Для ZIP ищется `main.py` или `__main__.py` на минимальной
   глубине. При равной глубине выбирается первый путь по алфавиту.
2. Проверка читает только выбранный файл из ZIP. Лимиты составляют 5 МиБ для
   загрузки, 256 записей в ZIP и 512 КиБ для проверяемого файла Python.
3. `ast.parse` проверяет синтаксис без исполнения программы. В файле должна быть
   хотя бы одна инструкция. Если синтаксис неверен, в отчёте указывается строка,
   когда парсер её сообщает.

Этого достаточно, чтобы отличить исходники с корректным синтаксисом от пустых
файлов, битых архивов и проектов из одного README. Импорты, зависимости и
поведение программы во время выполнения находятся за пределами этой эвристики.

## Демонстрация API

Откройте Swagger или выполните команды при запущенном Compose.

```bash
demo_dir=$(mktemp -d)
printf 'print("hello")\n' > "$demo_dir/main.py"
printf 'if:\n' > "$demo_dir/broken.py"

curl -i http://localhost:8000/submissions \
  -F 'student_id=student-01' -F 'assignment_id=hw-3' \
  -F "file=@$demo_dir/main.py"

curl -i http://localhost:8000/submissions \
  -F 'student_id=student-02' -F 'assignment_id=hw-3' \
  -F "file=@$demo_dir/broken.py"

curl http://localhost:8000/assignments/hw-3/reports
```

Обе загрузки дают `201`, а сводка нового задания показывает один зелёный и один
красный отчёт. Возьмите `submission_id` из любого ответа для запроса
`GET /submissions/{submission_id}/report`. Карточки видны и в браузере по ID
задания `hw-3`.

Для демонстрации сбоя выполните `docker compose stop analysis`, повторите
загрузку и получите `503` с ID сохранённой сдачи. Затем выполните
`docker compose start analysis` и повторите анализ по этому ID из Swagger или
карточки. После `docker compose stop store` загрузка даст `503` с именем
`store`. Запустите его снова командой `docker compose start store`.

## Тесты

Команды выполняются из `task_3` под Python 3.12.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Тесты проходят через три HTTP-приложения с временными SQLite и файловым
хранилищем. Они проверяют порядок вызовов, сохранность данных после повторной
инициализации сервисов, красный и зелёный отчёты, сводку, отказы и
восстановление.
